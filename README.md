# 勤怠管理システム(第1段階)

社内スタッフ用の勤怠・シフト・報酬管理Webアプリ。打刻・簡易本人確認・月単位シフト登録・確定受取金額表示・振込申請・固定支払・未出勤アラートの機能を実装しています。

## 技術構成

- **フレームワーク**: Next.js 16 (App Router / TypeScript / Tailwind CSS)
- **DB**: PostgreSQL(本番は [Supabase](https://supabase.com) を想定)+ Prisma 7(`@prisma/adapter-pg`)
- **メール送信**: [Resend](https://resend.com)
- **デプロイ**: Vercel を想定(`vercel.json` に未出勤アラート用の Cron 設定あり)
- **位置情報**: ブラウザ標準の Geolocation API で取得し記録のみ行う(HTTPS環境が必須。許可拒否・取得失敗時は位置情報を空欄のまま打刻を通す。距離チェック・ブロックは行わない)

## セットアップ

### 1. 依存パッケージのインストール

```bash
npm install
```

### 2. 環境変数の設定

`.env.example` を `.env` にコピーして値を設定してください。

```bash
cp .env.example .env
```

| 変数名 | 内容 |
|---|---|
| `DATABASE_URL` | PostgreSQL接続文字列(Supabaseの Database > Connection string) |
| `ADMIN_PASSWORD` | 管理者画面(`/admin`)用パスワード |
| `SESSION_SECRET` | Cookie署名用のランダムな秘密文字列(32文字以上推奨) |
| `RESEND_API_KEY` | Resend の APIキー |
| `MAIL_FROM` | 送信元メールアドレス(Resendで検証済みドメイン) |
| `CRON_SECRET` | 未出勤アラートAPI(`/api/cron/no-show-check`)を保護する秘密文字列 |

### 3. DBスキーマの反映

```bash
npx prisma migrate dev
```

### 4. 初期管理者アドレスの投入

`prisma/seed.ts` に初期管理者アドレス(t-ito@kjgroup.info)が登録されています。

```bash
npx prisma db seed
```

### 5. 開発サーバー起動

```bash
npm run dev
```

`http://localhost:3000` で社員コード入力画面が表示されます。

### 6. 他のWi-Fi・外部ネットワークからのアクセス(開発中の一時公開)

開発サーバーを起動したまま、以下のコマンドで [Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/connections/connect-apps) の Quick Tunnel を立てると、ローカルの開発サーバーに `https://xxxxx.trycloudflare.com` のようなURLで社内Wi-Fi外・スマホの4G/5G回線からもアクセスできます(Cloudflareアカウント不要)。

```bash
cloudflared tunnel --url http://localhost:3000
```

コンソールに表示される `https://xxxxx.trycloudflare.com` のURLをスマホで開いてください。

**注意点**
- このURLは `cloudflared` を起動するたびにランダムに変わります(アカウントなしのQuick Tunnelの仕様)。固定URLが必要な場合はCloudflareアカウントで名前付きトンネルを作成してください。
- 開発サーバー(`npm run dev`)と `cloudflared` の両方をPCで起動し続けている間だけアクセス可能です。PCをスリープ・シャットダウンすると繋がらなくなります。
- `next.config.ts` の `allowedDevOrigins` に `*.trycloudflare.com` を許可済みのため、追加設定なしでServer Actions(打刻・シフト登録等)も動作します。
- あくまで開発中の一時的な動作確認用です。継続的に社外からアクセスできる本番環境が必要な場合は、Vercel等への正式デプロイ([技術構成](#技術構成)参照)を行ってください。

## 画面構成

- `/` : 社員コード入力(スタッフ本人確認。共通パスワード等の追加認証はありません)
- `/clock` : ログイン後のホーム画面(下記参照)
- `/history` : 自分の打刻履歴一覧(スタッフ本人・全期間)
- `/shift` : 自分のシフト一覧(編集・複製・削除)
- `/shift/new` : シフト新規登録ウィザード(下記参照)
- `/shift/[id]` : シフト1件の個別編集(スタッフ本人)
- `/payment/request` : 振込申請(申請支払のスタッフのみ。固定支払のスタッフはアクセス不可)
- `/payment/history` : 自分の振込申請履歴(スタッフ本人・他スタッフ分は閲覧不可)
- `/admin/gate` : 管理者パスワード入力
- `/admin` : ダッシュボード
- `/admin/staff` : スタッフ(社員コード対応リスト)の登録・編集・在籍状態管理
- `/admin/staff/[id]` : スタッフ詳細(生年月日・連絡先・銀行口座・支払方法・固定支払スケジュール)の編集
- `/admin/shifts` : 全スタッフのシフト一覧(スタッフ・日付・帯/スポットで絞り込み、編集・削除)
- `/admin/shifts/history` : シフト変更履歴(登録・変更・削除)
- `/admin/records` , `/admin/records/[id]` : 打刻記録の一覧(スタッフ絞り込み可)・手動修正・削除(変更履歴を保持)
- `/admin/payments` : 振込申請一覧・振込済み処理
- `/admin/admins` : 通知先の管理者メールアドレスの登録・編集

### ホーム画面(`/clock`)

ログイン(社員コード入力)後は直接シフト登録画面ではなくホーム画面に遷移します。スマホでの利用を想定し、上から次の優先順位で表示しています。

1. 現在日時(日付・曜日・時刻をリアルタイム表示)
2. 出勤・退勤ボタン(現在の打刻状態に応じて片方のみ活性化。連続で同じ種別を打刻できないようにしています)
3. 今日の打刻履歴(出勤/退勤時刻、未打刻の場合は「未打刻」表示)
4. 今月の確定受取金額(計算方法は下記)
5. 支払関連情報 — 固定支払のスタッフには次回支払予定日、申請支払のスタッフには申請済み金額・振込申請可能額・振込申請ボタンを表示
6. 今月の打刻履歴(日付・曜日・出勤時刻・退勤時刻)
7. シフト登録への導線

### シフト登録ウィザード(`/shift/new`)

スタッフ本人が、以下の流れで1ヶ月分をまとめて登録します。入力途中で「戻る」を押しても内容は保持されます。

1. 対象月を選択(前3ヶ月〜先6ヶ月をプルダウンで選択可)
2. 稼働区分(帯稼働 / スポット稼働)を選択
3. 稼働キャリアを選択(SoftBank・Y!mobile / au・UQ / docomo・ahamo / 楽天モバイル / その他〈自由記述〉)
4. 稼働先店舗名を入力(自由記述)
5. 稼働予定時間(開始・終業)をプルダウンで選択(30分刻み。終業が開始より前の場合は翌日終業として登録)
6. 対象月の日付一覧からチェックボックスで稼働日を選択(土日は色分け表示。既に登録済みの日は「登録済み」として自動チェック・ロックされ、重複登録されません)。**スポット稼働の場合は選択した日ごとに単価入力欄が表示され、全日分入力するまで次へ進めません。**
7. **帯稼働のみ**: 対象月合計の受取予定単価を任意入力(数字のみ、3桁カンマ区切り表示。空欄のままでも登録可能。スポット稼働ではこのステップ自体がスキップされます)
8. 内容を確認し、一括登録

登録済みの月を再度開いて日付を追加しなくても、受取予定単価だけを更新して保存できます。

## 受取金額の計算について(重要な設計判断)

「今月の確定受取金額」は **サーバー側**([src/lib/earnings.ts](src/lib/earnings.ts))で計算しており、クライアント側では再計算していません。**現時点で稼働が完了・確定している分の累計のみを表示し、今後の稼働予定分は含みません。** 月末の最終支払額そのものではありません。

- **帯稼働**: 月間受取予定単価 ÷ 月間予定稼働日数(**円未満切り捨て**)で1稼働あたりの内部単価を算出し、確定済みの日数分だけ積み上げます。この内部単価・月間受取予定単価はスタッフ画面には一切表示しません(「◯◯円/日」等の表示はなし)。月間受取予定単価が未入力の場合は金額を推測せず、確定受取金額を **「－」** として表示します(0円と断定しません)。
- **スポット稼働**: シフト登録時に稼働日ごとに単価を個別入力し、確定した日の単価だけを合算します。
- ある稼働予定日が「確定」扱いになるのは、その日のシフトに対して **出勤・退勤の両方の打刻が記録されている場合のみ** です。現時点では「トラブル」「欠勤」などのステータスを手動で設定する機能がないため、出退勤の打刻有無のみで自動判定しています。欠勤等で打刻が揃わない日は単に加算されないだけで、一度加算してから減算するような処理はしていません。
- 月間受取予定単価は基本報酬・インセンティブ・各種加算減算を区別せず1つの数値として扱う設計です。将来インセンティブ等を分けて管理する必要が生じた場合は、`MonthlyEarningTarget` テーブルへのフィールド追加、または加算・減算を別テーブルで管理する形で拡張できます(今回は未実装)。

## 支払方法・振込申請・固定支払

スタッフごとに支払方法(`/admin/staff/[id]`)を **固定支払** か **申請支払** のいずれかに設定します。

### 固定支払
会社が指定した締日・支払月(当月/翌月/翌々月)・支払日(具体的な日、または「月末」)から、次回支払予定日を自動計算して表示します([src/lib/payment.ts](src/lib/payment.ts))。月末指定は2月・うるう年も含めて正しく計算します。振込申請ボタンは表示しません。

### 申請支払
スタッフ本人が、確定済み報酬のうちまだ申請していない金額の範囲内で、好きなタイミングに振込申請できます。

- 振込申請可能額 = 全期間の確定受取金額の累計 − (申請中+振込済みの申請金額の合計)。同じ確定報酬を二重に申請できないよう、まだ処理されていない「申請中」の分もこの時点で差し引きます。
- 申請時の金額チェックはサーバー側で必ず再計算します(クライアントから送られた金額をそのまま信用しません)。
- 「確定した報酬額」(`MonthlyEarningTarget`/`Shift.unitAmount` から算出)と「実際に振り込んだ金額」(`TransferRequest`)は別のモデルとして管理しており、確定=支払済みとは扱いません。
- 管理者は `/admin/payments` で申請一覧を確認し、「振込済みにする」操作で実際の振込金額・処理者名を記録できます。このアプリには個別の管理者アカウントがなく共通パスワードのみのため、「操作した管理者」は処理のたびに自由記述で入力してもらう方式にしています。

## 打刻記録の変更履歴

管理者が打刻記録を手動修正・削除すると、変更前後の内容と処理者名(自由記述)を `ClockRecordHistory` に記録します(振込申請の処理者名と同様、個別管理者アカウントがないための簡易対応です)。

## 未出勤アラートの運用について(重要)

`/api/cron/no-show-check` は `Authorization: Bearer <CRON_SECRET>` ヘッダーで保護された、
シフト開始時刻から5分経過しても出勤打刻がないスタッフを検出してメール送信するAPIです。

**Vercelの無料(Hobby)プランは Cron の実行間隔が1日1回に制限されており、
「5分経過で検知」という要件を満たせません。** また、Hobbyプランでは分間隔のCron設定自体が
デプロイをブロックするため、`vercel.json` には現在Cron設定を含めていません。

代わりに、無料の外部Cronサービス(例: [cron-job.org](https://cron-job.org))から
`https://<your-domain>/api/cron/no-show-check` に `Authorization: Bearer <CRON_SECRET>` ヘッダー付きで
1〜2分間隔にGETリクエストを送る運用としています。

(将来 Vercel **Pro プラン**に切り替える場合は、`vercel.json` に
`{ "crons": [{ "path": "/api/cron/no-show-check", "schedule": "*/1 * * * *" }] }`
を再度追加すれば、`CRON_SECRET` 環境変数を設定するだけでVercel Cronが自動でAuthorizationヘッダーを付与します)

## 既知の制約・設計判断

- 社員コードのみによる本人確認で、パスワード等による厳密な本人確認・なりすまし防止は行っていません(要件通り)。
- 打刻の二重打刻・押し忘れは完全には防止していません(ホーム画面のボタンは状態に応じて活性/非活性を切り替えますが、データ不整合が生じた場合は管理者が `/admin/records` で事後修正する運用を前提にしています)。
- 拠点との距離による打刻ブロックは行いません(位置情報は記録のみ)。
- シフトのないスタッフが打刻すると、店舗名は空欄のまま時刻と位置情報のみ記録されます。
- 日付・時刻はすべて JST(Asia/Tokyo)を基準に扱っています。
- 個別の管理者アカウント・ログインは存在せず、共通の管理者パスワードのみです(第1段階からの方針を踏襲)。そのため「操作した管理者」の記録は自由記述の氏名入力で代替しています。個別アカウントが必要になった場合は認証まわりの追加設計が必要です。
- 月間受取予定単価は「基本報酬+インセンティブ+加算-減算」を分けて管理する構造にはなっておらず、1つの数値として扱います。ただし `MonthlyEarningTarget` はスタッフ×対象月単位で独立したテーブルのため、将来インセンティブ等を分離管理したくなった場合も既存データを壊さずにテーブル追加で拡張できます。
- 過去のシフト・確定金額・振込申請・支払履歴は、スタッフの支払方法や口座情報を後から変更しても書き換わりません(各レコードが作成時点の値をそのまま保持するため)。
